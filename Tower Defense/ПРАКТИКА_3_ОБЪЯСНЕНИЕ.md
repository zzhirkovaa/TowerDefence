# Третья практическая: параллельные Jobs

Этот файл объясняет, **что изменилось в проекте**, зачем это сделано и как работает код. Полные листинги ниже имеют названия исходных скриптов и совпадают с текущими файлами проекта.

## 1. Суть задания и выбор систем

В третьей практической нужно найти системы, где множество entity выполняет одинаковую независимую работу, и перевести их на Jobs. В tower defense это прежде всего движение и стамина врагов:

| Скрипт | До практической | После практической |
|---|---|---|
| `MoveToTowerSystem.cs` | `foreach` последовательно двигал врагов | `MoveToTowerJob : IJobEntity` обрабатывает врагов через `ScheduleParallel` |
| `StaminaSystem.cs` | `foreach` последовательно проверял запас сил | `StaminaJob : IJobEntity` проверяет и восстанавливает его через `ScheduleParallel` |
| `RemoveAtTowerSystem.cs` | `foreach` последовательно проверял расстояние до башни | `RemoveAtTowerJob : IJobEntity` проверяет его параллельно и записывает удаление через `ECB.ParallelWriter` |

Видимый результат остаётся тем же: враги появляются, идут к башне, отдыхают при исчерпании стамины, затем продолжают идти. `EnemySpawnerSystem` оставлен последовательным: он выдаёт одного врага раз в интервал, и распределять эту единичную операцию между потоками нечего. `RemoveAtTowerSystem` также переведён на параллельную Job: она независимо проверяет расстояние для каждого врага и записывает удаление через `EntityCommandBuffer.ParallelWriter`.

## 2. Теория: что такое Job и зачем она здесь

**Поток** — линия выполнения кода процессором. Последовательный `foreach` обрабатывает врагов один за другим. **Job** — задача для планировщика Unity. `ScheduleParallel` позволяет обрабатывать подходящие entity на рабочих потоках, когда у них достаточно независимой работы.

`IJobEntity` — Job для ECS-сущностей. Её метод `Execute` выполняется для **одной подходящей entity**. Unity сама выбирает entity по параметрам `Execute` и атрибутам Job. Например:

```csharp
void Execute(ref LocalTransform transform, in MoveSpeed speed, ref Stamina stamina)
```

`ref` означает чтение **и изменение** компонента, `in` — только чтение. Каждый вызов `Execute` получает компоненты своего врага. Движение одного врага не требует результата движения другого, поэтому обработка подходит для параллельного выполнения.

`[BurstCompile]` помогает эффективно компилировать подходящий код, но **сам по себе не запускает несколько потоков**. Для этого Job планируется через `ScheduleParallel`.

### Что означает `state.Dependency = job.ScheduleParallel(state.Dependency)`

`ScheduleParallel` ставит Job в очередь планировщика. Он **не означает, что `Execute` уже закончился**, когда выполнение перешло к следующей строке `OnUpdate`. Входной `state.Dependency` сообщает о работах, которые должны завершиться прежде. Возвращённый `JobHandle` записывается обратно в `state.Dependency`, чтобы следующие системы учитывали новую Job.

После планирования Jobs в системах нет кода, который немедленно читает их результаты. Поэтому `state.Dependency.Complete()` здесь не вызывается: принудительное ожидание остановило бы главный поток и уменьшило пользу от Jobs.

## 3. Система движения: `MoveToTowerSystem.cs`

**Что изменилось:** прежний цикл `foreach` перенесён в `MoveToTowerJob.Execute`. Система теперь только один раз читает положение башни, создаёт Job и планирует её.

**Полный листинг — `Assets/Scripts/Systems/MoveToTowerSystem.cs`:**

```csharp
using Unity.Burst;
using Unity.Entities;
using Unity.Mathematics;
using Unity.Transforms;

public partial struct MoveToTowerSystem : ISystem
{
    [BurstCompile]
    [WithAll(typeof(CanMove))]
    partial struct MoveToTowerJob : IJobEntity
    {
        public float3 TowerPosition;
        public float DeltaTime;

        void Execute(ref LocalTransform transform, in MoveSpeed speed, ref Stamina stamina)
        {
            var position = transform.Position;
            var target = new float3(TowerPosition.x, position.y, TowerPosition.z);
            var offset = target - position;
            var distance = math.length(offset);
            if (distance <= speed.ReachDistance)
                return;

            var direction = offset / distance;
            var step = math.min(speed.Value * DeltaTime, distance - speed.ReachDistance);
            transform.Position = position + direction * step;
            transform.Rotation = quaternion.LookRotationSafe(direction, math.up());
            stamina.Current = math.max(0f, stamina.Current - stamina.DrainPerSecond * DeltaTime);
        }
    }

    public void OnCreate(ref SystemState state)
    {
        state.RequireForUpdate<TowerTarget>();
        state.RequireForUpdate<MoveSpeed>();
    }

    [BurstCompile]
    public void OnUpdate(ref SystemState state)
    {
        var towerEntity = SystemAPI.GetSingletonEntity<TowerTarget>();
        var towerPosition = SystemAPI.GetComponent<LocalTransform>(towerEntity).Position;
        var job = new MoveToTowerJob
        {
            TowerPosition = towerPosition,
            DeltaTime = SystemAPI.Time.DeltaTime
        };
        state.Dependency = job.ScheduleParallel(state.Dependency);
    }
}
```

### Разбор листинга

1. `[WithAll(typeof(CanMove))]` выбирает врагов с **включённым** `CanMove`. Отдыхающие враги в движение не попадают.
2. `TowerPosition` и `DeltaTime` — значения, которые система передаёт Job. Положение башни не приходится искать отдельно для каждого врага.
3. `Execute(ref LocalTransform, in MoveSpeed, ref Stamina)` получает позицию и стамину конкретного врага для записи, а скорость — только для чтения.
4. Цель состоит из координат X/Z башни и высоты Y врага: враг идёт по горизонтали, не поднимаясь к центру высокой башни.
5. Если расстояние меньше `ReachDistance`, движение прекращается. Иначе вычисляются направление, шаг `скорость × время кадра`, новый поворот и расход стамины.
6. `state.Dependency = job.ScheduleParallel(state.Dependency)` планирует эту работу для подходящих врагов.

Позиция башни передаётся Job как значение `float3`, только для чтения. Каждый вызов `Execute` пишет лишь в компоненты своего врага, а не в компоненты соседей или башни.

## 4. Система стамины: `StaminaSystem.cs`

**Что изменилось:** проверка и восстановление стамины перенесены из последовательного `foreach` в `StaminaJob.Execute`.

**Полный листинг — `Assets/Scripts/Systems/StaminaSystem.cs`:**

```csharp
using Unity.Burst;
using Unity.Entities;
using Unity.Mathematics;

[UpdateBefore(typeof(MoveToTowerSystem))]
public partial struct StaminaSystem : ISystem
{
    [BurstCompile]
    [WithOptions(EntityQueryOptions.IgnoreComponentEnabledState)]
    partial struct StaminaJob : IJobEntity
    {
        public float DeltaTime;

        void Execute(ref Stamina stamina, EnabledRefRW<CanMove> canMove)
        {
            if (canMove.ValueRO && stamina.Current <= 0f)
                canMove.ValueRW = false;

            if (!canMove.ValueRO)
            {
                stamina.Current = math.min(
                    stamina.Max,
                    stamina.Current + stamina.RegenPerSecond * DeltaTime);

                if (stamina.Current >= stamina.MinToMove)
                    canMove.ValueRW = true;
            }
        }
    }

    public void OnCreate(ref SystemState state)
    {
        state.RequireForUpdate<Stamina>();
    }

    [BurstCompile]
    public void OnUpdate(ref SystemState state)
    {
        var job = new StaminaJob
        {
            DeltaTime = SystemAPI.Time.DeltaTime
        };
        state.Dependency = job.ScheduleParallel(state.Dependency);
    }
}
```

### Разбор листинга

1. `EnabledRefRW<CanMove>` даёт возможность прочитать и переключить включённость `CanMove` **конкретного врага**.
2. `[WithOptions(EntityQueryOptions.IgnoreComponentEnabledState)]` необходим: отдыхающий враг имеет выключенный `CanMove`, но Job всё равно должна найти его и восстановить стамину. Без этой настройки он мог бы так и остаться стоять.
3. При `Current <= 0` Job выключает движение. Пока оно выключено, прибавляет `RegenPerSecond × DeltaTime`, не превышая `Max`.
4. При достижении `MinToMove` Job снова включает движение.
5. `[UpdateBefore(typeof(MoveToTowerSystem))]` ставит систему стамины перед системой движения. Передача `state.Dependency` сохраняет зависимость между запланированными Jobs.

Здесь важно различать **порядок вызова систем** и **окончание их Jobs**. Атрибут `UpdateBefore` задаёт первый; зависимости Jobs обеспечивают второй. Job движения тоже обращается к `Stamina` и состоянию `CanMove`, поэтому должна учитывать работу Job стамины.

## 6. Откуда эти компоненты берутся

Эти два Baker-файла тоже не менялись в третьей практической, но без них непонятно, почему созданный враг подходит под Job и как находится башня.

### `EnemyAuthoring.cs` — настройки и запекание врага

**Полный листинг — `Assets/Scripts/Authoring/EnemyAuthoring.cs`:**

```csharp
using Unity.Entities;
using UnityEngine;

public class EnemyAuthoring : MonoBehaviour
{
    public float Speed = 3f;
    public float ReachDistance = 0.35f;
    public float MaxStamina = 2f;
    public float StaminaDrainPerSecond = 2.5f;
    public float StaminaRegenPerSecond = 2f;
}

class EnemyBaker : Baker<EnemyAuthoring>
{
    public override void Bake(EnemyAuthoring authoring)
    {
        var entity = GetEntity(TransformUsageFlags.Dynamic);

        AddComponent(entity, new MoveSpeed
        {
            Value = authoring.Speed,
            ReachDistance = authoring.ReachDistance
        });
        AddComponent(entity, new Stamina
        {
            Current = authoring.MaxStamina,
            Max = authoring.MaxStamina,
            DrainPerSecond = authoring.StaminaDrainPerSecond,
            RegenPerSecond = authoring.StaminaRegenPerSecond,
            MinToMove = authoring.MaxStamina * 0.5f
        });
        AddComponent<CanMove>(entity);
        SetComponentEnabled<CanMove>(entity, true);
    }
}
```

`EnemyBaker` добавляет врагу `MoveSpeed`, `Stamina` и включённый `CanMove`. Поэтому новый враг может сразу идти, а обе Jobs получают нужные данные. Значения из Inspector префаба могут отличаться от значений по умолчанию в этом C#-файле.

## 7. Параллельное удаление у башни

`RemoveAtTowerSystem` теперь планирует `RemoveAtTowerJob` после системы движения. Она читает положение и скорость каждого врага, независимо проверяет расстояние до башни и при достижении цели записывает команду удаления. Позиция башни передаётся в Job значением `float2 TowerPosition`.

**Полный листинг — `Assets/Scripts/Systems/RemoveAtTowerSystem.cs`:**

```csharp
using Unity.Burst;
using Unity.Entities;
using Unity.Mathematics;
using Unity.Transforms;

[UpdateAfter(typeof(MoveToTowerSystem))]
public partial struct RemoveAtTowerSystem : ISystem
{
    [BurstCompile]
    partial struct RemoveAtTowerJob : IJobEntity
    {
        public float2 TowerPosition;
        public EntityCommandBuffer.ParallelWriter CommandBuffer;

        void Execute(Entity entity, [ChunkIndexInQuery] int sortKey,
            in LocalTransform transform, in MoveSpeed speed)
        {
            var offset = TowerPosition - transform.Position.xz;
            var reach = speed.ReachDistance;
            if (math.lengthsq(offset) <= reach * reach)
                CommandBuffer.DestroyEntity(sortKey, entity);
        }
    }

    public void OnCreate(ref SystemState state)
    {
        state.RequireForUpdate<TowerTarget>();
        state.RequireForUpdate<MoveSpeed>();
        state.RequireForUpdate<EndSimulationEntityCommandBufferSystem.Singleton>();
    }

    [BurstCompile]
    public void OnUpdate(ref SystemState state)
    {
        var tower = SystemAPI.GetSingletonEntity<TowerTarget>();
        var towerPosition = SystemAPI.GetComponent<LocalTransform>(tower).Position;
        var ecb = SystemAPI.GetSingleton<EndSimulationEntityCommandBufferSystem.Singleton>()
            .CreateCommandBuffer(state.WorldUnmanaged);
        var job = new RemoveAtTowerJob
        {
            TowerPosition = towerPosition.xz,
            CommandBuffer = ecb.AsParallelWriter()
        };
        state.Dependency = job.ScheduleParallel(state.Dependency);
    }
}
```

В `Execute` параметр `Entity entity` обозначает проверяемого врага, а `[ChunkIndexInQuery] int sortKey` даёт ключ для упорядочивания команд, записанных параллельно. Обычный ECB не предназначен для одновременной записи несколькими потоками, поэтому Job получает `ecb.AsParallelWriter()` и вызывает `CommandBuffer.DestroyEntity(sortKey, entity)`.

`state.Dependency = job.ScheduleParallel(state.Dependency)` связывает проверку с ранее запланированным движением. ECB создан через `EndSimulationEntityCommandBufferSystem.Singleton`. В установленной версии Entities этот Singleton отслеживает Jobs, пишущие в созданный через него буфер, и ждёт их перед воспроизведением. Поэтому немедленный `state.Dependency.Complete()` здесь не нужен.

`EnemySpawnerSystem` остаётся последовательной: она создаёт одного врага через заданный интервал.

## 8. Порядок работы в кадре

```text
StaminaSystem планирует StaminaJob
    ↓ зависимость
MoveToTowerSystem читает башню и планирует MoveToTowerJob
    ↓ зависимость
RemoveAtTowerSystem планирует RemoveAtTowerJob с ECB.ParallelWriter
    ↓
EndSimulationEntityCommandBufferSystem воспроизводит команды
```

Планирование Job не равняется немедленному завершению её `Execute`. Стрелки показывают порядок необходимых результатов, а не выполнение всего кода на одном потоке.

## 9. Проверка и пределы результата

Unity успешно скомпилировала новые Jobs. В автоматической проверке Play Mode волна завершилась, а у отслеживаемого врага были зафиксированы **остановка и последующее возобновление движения**. Временный проверочный скрипт после проверки удалён.

Это проверка правильности поведения, **не измерение ускорения**. На волне из 12 врагов расходы на планирование Jobs могут перекрывать выигрыш. Чтобы утверждать, что игра стала быстрее, нужно сравнить старую и новую реализации при большой волне в Unity Profiler или окне Entities → Systems.

## 10. Вопросы, которые могут задать на защите

**Почему выбраны именно движение и стамина?** Они выполняют одинаковые независимые расчёты для каждого врага. Спавнер создаёт одного врага за интервал, поэтому распараллеливать его нечего.

**Что делает `IJobEntity`?** Описывает обработку одной подходящей ECS-сущности. Unity вызывает `Execute` для всех подходящих entity.

**Почему `ref` у позиции и стамины, но `in` у скорости?** Позиция и текущая стамина изменяются; скорость только читается.

**Что делает `ScheduleParallel`?** Планирует обработку подходящих entity на рабочих потоках. Он не ждёт завершения Job перед возвратом.

**Зачем `state.Dependency`?** Чтобы Job дождалась нужных предыдущих работ, а следующие системы знали о ней.

**Почему стамине нужен `IgnoreComponentEnabledState`?** Чтобы восстановить запас врага даже тогда, когда `CanMove` выключен.

**Где здесь гонка данных?** Jobs движения и стамины пишут компоненты только своего врага; Job удаления лишь читает их и записывает команды в потокобезопасный `ParallelWriter`. Общая позиция башни передаётся только для чтения. Зависимости связывают работу систем.

**Зачем `EntityCommandBuffer.ParallelWriter`?** Несколько рабочих потоков могут одновременно обнаружить врагов у башни. `ParallelWriter` позволяет им записать команды удаления; фактическое удаление происходит при воспроизведении ECB.

**Значит ли `[BurstCompile]`, что система параллельная?** Нет. Burst отвечает за компиляцию; параллельное планирование задаёт `ScheduleParallel`.

## 11. Короткий рассказ для преподавателя

> Я перевела движение, стамину и проверку достижения башни на параллельные `IJobEntity`, потому что каждая из этих систем выполняет независимую работу для каждого врага. Системы планируют Jobs через `ScheduleParallel(state.Dependency)`. `MoveToTowerJob` двигает врагов, `StaminaJob` управляет отдыхом, а `RemoveAtTowerJob` проверяет расстояние до башни и через `EntityCommandBuffer.ParallelWriter` записывает удаление дошедших врагов. Спавнер оставлен последовательным, так как создаёт одного врага за интервал.
